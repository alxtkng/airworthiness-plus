# Restore Test, 19 November 2026

REQ-153, REQ-154; hazards H-007 and H-009; threats TH-023, TH-040 and TH-042.

## What This Is, and Is Not

A full backup and restore of the sample organisation, run by the scripts and commands in `operations/` exactly as written, in the build environment: PostgreSQL 16, with the service's database roles. **It was not run on the server**, which the build session cannot reach. It shows that the procedure works and what it proves; the same test is to be run on the server before private beta ends and its record added beside this one.

Who: Claude, in the build session. No real record was involved.

## Roles Used

| Role | Rights | Used For |
|---|---|---|
| Owner | Owns the tables; not a superuser | Migrations; stating the highest serial |
| Service login | Member of `airworthiness_application` only | Issuing certificates, as the application would |
| Backup | Can read every record of every organisation; can write nothing | The backup; the check of the records |

An attempt to change a record as the backup role was refused by the database: permission denied.

## Steps and Results

| Step | What Was Done | Result |
|---|---|---|
| 1 | State of the records noted | 75 history entries, 7 aircraft, 7 certificates, 3 access log entries. Fingerprint of the history, the SHA-256 of every entry's hash in order: `3bcb5a74…c9aa1f6`. Highest certificate serial 1 |
| 2 | `backup.sh`, as the backup role, encrypted to a key made for the test | 235,881 bytes in 0.1 seconds; checksum file written and checked |
| 2a | The backup file read without its key | It begins `age-encryption.org/v1`; no aircraft registration can be found in it; decrypting with a different key fails with no identity matched (TH-040) |
| 3 | After the backup, a certificate issued in the live records, as the service login | UK.CAO.[Number]-ARC-0002. The live records now hold a serial the backup does not |
| 4 | `restore.sh` into a new, empty database | Restored in 0.3 seconds |
| 4a | `restore.sh` again into the same database | Refused: the database is not empty. Nothing was restored |
| 5 | State of the restored records | 75 history entries, 7 aircraft, 7 certificates, 3 access log entries. Fingerprint `3bcb5a74…c9aa1f6`: identical to step 1 |
| 5a | `check_records`, as the backup role | 0 chain problems; 0 record types not matching their history; The Records Agree with Their History |
| 5b | The record rules in the restored database | 26 tables with forced row-level security, 29 policies, 121 triggers: the same counts as the live database |
| 5c | The service login against the restored database | Sees 0 aircraft with no organisation set; an attempt to change the history is refused |
| 6 | Highest serial in the restored records | 1. Without a correction the next certificate would be ARC-0002 a second time (hazard H-007) |
| 6a | `set_serial_floor`, as the owner, stating 2 as the highest serial issued | Highest Serial in the Records 1; Highest Serial Stated 2; Next Serial 3 |
| 6b | A certificate issued in the restored records, as the service login | UK.CAO.[Number]-ARC-0003. The serial lost with the live records is not used again (REQ-154) |

## Verdict

Passed.

- The records and their whole history came back identical, and were shown to be so by a check that does not rely on the restore having worked.
- The rules that protect the records came back with them.
- A backup cannot be read without its key.
- A certificate serial is not repeated after a restore, provided the highest serial issued is stated before the service is opened again. That step depends on a person, and is in the procedure.

## Limits

- The database is small. The times say nothing about a database of real size; they are measured again when there is one.
- The test restored on the same machine, where the roles already existed. On a new server the roles are created first (`backup-and-restore.md`, Restoring).
- The backup was not copied off the machine. Where backups are kept is not yet decided (Issue 27).
