# ADR-0011 Synthetic work card attestation

**Status** Proposed for local rehearsal. **Requirement** REQ-380.

This policy applies to a single synthetic work card completion on sample Part-ML aircraft in an isolated tenant. Set `AIRWORTHINESS_SYNTHETIC_WORK_CARD_ATTESTATION=true` only in a disposable training environment. The path also requires a package reference starting `WP-SYNTHETIC-`. Use original fictional instructions, accounts, grants and measurements. Use the existing package workflow to issue the card and record completion with source evidence before the performer attests to it.

| Action | Policy |
|---|---|
| Sign-in or step-up | Authentication by the existing passkey with user verification or password and authenticator process in ADR-0005. Existing sessions may satisfy the five-minute verification window. |
| Review or cancel | Display the evidence so the performer can check it. Neither action saves consent. |
| Archive synthetic completion attestation | The signed-in account must have the work card evidence role and be linked to the named performer. The performer must be with the organisation and recorded as certifying staff on the attestation date. A current, unwithdrawn synthetic grant must match the literal scope `Synthetic work-card completion: ` followed by the aircraft type rating. Explicit consent is bound to the card version and the displayed authority. |
| Independent inspection | Existing work package procedure and qualification evidence continue to apply. The release checklist displays outstanding critical inspections. |
| Release to service | Existing evidence-recording procedure for an already-issued certificate. The synthetic grant is refused for this purpose and for regulated defect decisions. |

The review token authenticates what the server displayed, using the application secret and a ten-minute lifetime. It covers the work card event sequence and hash, the aircraft, source and revision IDs, the used revision, inspection status, actor, the grant and its dates. The server recomputes the content under the package lock. The staff record lock serialises authorisation withdrawals with archival. It stores the performer and authority, the application's attestation and recent verification times, and the reviewed content in one append-only record. An unchanged retry keeps the original record. A failed database write rolls back both archival and its history. The pilot does not request location, device ownership, clock-in evidence or disconnected operation.

**UK rules read on 28 November 2026.** CAO.A.055 sets the requirement for applicable current maintenance data and an agreed written work order before maintenance. CAO.A.060(h) requires an error-capturing method after a critical maintenance task. ML.A.801 governs release to service for Part-ML aircraft. These are operational rules. The pilot's synthetic role, literal scope, five-minute verification window and explicit review are project choices. Operation under Part-M, Part-145 or Part-CAMO needs a separate applicability assessment for the deployment and action. **Acceptable means of compliance.** AMC1 CAO.A.060(g) and AMC1 ML.A.402(b)(7) describe task sign-off after completion and identifying critical steps when grouping tasks for sign-off. The pilot uses one card-level action on already recorded work. An operational structured card and its instructions for individual steps need their own review. [CAA AMC for Part-CAO](https://regulatorylibrary.caa.co.uk/1321-2014/Content/Document%20Structure/05d%20CAO/3%20AMC/AMC1%20CAO%20A%20060%20g%20Maintenance.htm) [CAA AMC for Part-ML](https://regulatorylibrary.caa.co.uk/1321-2014/Content/Document%20Structure/05b%20ML/3%20AMC/AMC1%20ML%20A%20402%20b%207%20Performance.htm)

**UK signature terminology.** Article 26 sets the conditions for an advanced electronic signature, including high-confidence sole control and detectable changes. Article 3 defines a qualified electronic signature in terms of an advanced signature, a qualified creation device and a qualified certificate. The application records consent as a synthetic electronic attestation. Its server token and retained digest establish application and archive integrity within the local trust boundary. Independent issuer trust, signer-controlled signing credentials and a trusted timestamp require further evidence. [UK eIDAS Articles 3, 25 and 26](https://www.legislation.gov.uk/eur/2014/910/2026-09-30?view=extent)

**Export.** Aircraft and organisation archives contain `records/planning_workcardattestation.json` and the corresponding CSV and history. The `evidence` string is the original UTF-8 JSON text. Compute SHA-256 over that string's UTF-8 bytes and compare it with `sha256`. Use `reviewed_content.card_id`, `card_version` and `card_version_hash` to find the exact card event in the exported card history. The normal manifest and history verifier checks archive consistency. Independent signatory and signing-time trust and a receiving implementation remain outstanding.
