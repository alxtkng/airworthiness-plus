# ADR-0003: A Test Site Before the Server

Status: **Accepted, 20 November 2026.** Proposed that day in pull request 97 (Issue 96). Alex King gave the word to proceed, the pull request was merged on it, and he made the test site on Render the same day.

Date: 20 November 2026

## Context

- Alex King asked on 20 November 2026 for a test site only, at no cost, before anything goes live.
- The server of ADR-0001 was not reached that day: its address and access were not to hand. `operations/deployment.md` and ADR-0001 still stand for the live service.
- The service is one image and a PostgreSQL database with two roles (ADR-0001, ADR-0002). A test site is worth having only if it runs that image and keeps those two roles.
- The repository is public. Nothing secret may be in it, and no secret is given to an assistant (`operations/keys-and-secrets.md`, rule 2).
- One founder runs it, and he is new to software delivery. Each step done by hand is a step that can go wrong.
- The sample organisation can never be removed from a database once it is there, because nothing is deleted (REQ-131). It must never reach a database of real records.

## Options

### Option A. Wait for the Server

- For: one deployment, and it is the real one.
- Against: nothing can be seen running until the server is found, looked at and set up. It does not answer what was asked.

### Option B. A Static Host (Cloudflare Pages)

- For: free, and quick.
- Against: it serves files. It cannot run the image or a database, so it would show pictures of the pages and test nothing.

### Option C. A Free Container Host With a Database (Render)

Render builds the image from the `Dockerfile` in the repository, runs it on its free plan, and provides a free PostgreSQL 18. Its whole set-up is one file in the repository, `render.yaml`.

- For: the image is the one the pipeline builds, unchanged. HTTPS and a host name of its own, with no DNS record of ours changed. Every secret is generated by the host. The set-up can be made again from the file.
- Against: a second company holds the test site. The free service sleeps after 15 minutes without a request and takes about a minute to wake. The free database is deleted 30 days after it is made, with 14 days' grace. The free plan gives no way to run a command before the service starts and no terminal, so the owner's work cannot be done by hand as `operations/deployment.md` describes.

### Where the Owner's Work Is Done, Under Option C

| | At the Start of the Container | From the Pipeline |
|---|---|---|
| How | A program in the image does the owner's work, then starts the service in its place with the owner's credentials taken out of its environment | A workflow connects to the database from GitHub and does the owner's work there |
| Secrets typed by hand | None | The database's address and the owner's password, copied into GitHub, and again every 30 days when the free database is replaced |
| The database open to the internet | No | Yes, to GitHub's addresses |
| Where the owner's credentials are | In the host's environment values for the service, never in the running service | In GitHub's secrets |
| After the free database is replaced | The next start makes everything again | The secrets are copied in again by hand |

## Decision

Option C, with the owner's work done at the start of the container.

| Part | Choice | Reason |
|---|---|---|
| Host | Render, free plan, Frankfurt | Runs the image unchanged; a database with it; set up from one file |
| Set-up | `render.yaml` at the root of the repository | One file, reviewed like any other change; checked against Render's published schema |
| Database | PostgreSQL 18, free plan, closed to every address outside the host's own network | The version the pipeline tests against; no route in from the internet |
| Start | `python -m airworthiness_plus.sample.test_site`, then the `Dockerfile`'s own command, unchanged | A test fails the build if the two commands drift apart |
| Owner's work | `manage.py prepare_test_site`: migrations, the service's role, the sample organisation | The steps of First Deployment 2 to 4, done by a program because the host gives no terminal |
| Secrets | Generated by the host: the signing key, the service role's password, the Administrator's first password. The owner's password is the host's own | None in the repository, none typed, none seen by an assistant |
| Deploys | After the pipeline has passed on `main`, and not before | The test site never runs code the checks refused |

### How the Fixed Rules Are Kept

| Rule | On the Test Site |
|---|---|
| The running service never holds the owner's credentials (ADR-0002, TH-024) | The service is started with every `AIRWORTHINESS_TEST_SITE_` value and the owner-work flag removed from its environment. Tested, and shown on the running processes in the rehearsal |
| The service's role is a member of `airworthiness_application` and nothing more | Made so, and an existing role that is anything else is refused, not altered |
| A password is never sent where it can be logged | The role's password is hashed before it is sent to the database (SCRAM-SHA-256). Tested |
| The sample never reaches real records | The owner's work runs only on a database it found empty and marked as the test site's own. Any other database is refused. Tested |
| No secret in the repository (TH-063) | A test fails the build if `render.yaml` holds a value for any password or key |

## Consequences

- There is something to sign in to and try, for nothing, before the server is touched.
- The image now holds one module and one command that exist for the test site. Neither does anything unless it is started by name with the test site's own values, and the command refuses a database that is not marked for it.
- The owner's credentials are in the host's environment values for the test site's service. Whoever can sign in to the Render account can read them. On the server they are held by Alex King alone and never stored with the service (`operations/keys-and-secrets.md`). This difference is accepted for a site that holds the sample only.
- Render becomes a company that holds a copy of the application and the sample. It holds no personal data and no record of any organisation, so it is not a processor under the data protection record. If a real record were ever entered there, it would be.
- The test site shows that the image runs, that the two roles work on a hosted database, and that the pages behave over real HTTPS. It shows nothing about the server.

## What It Does Not Show

- The 17 checks of the server and its reverse proxy (`assurance/asvs.md`, To Be Verified at Deployment). The proxy on the test site is Render's, not ours.
- Backup and restore on the server (REQ-150 to REQ-153). The free database has no backup.
- No exit item of `assurance/readiness-review.md` is met by it.
